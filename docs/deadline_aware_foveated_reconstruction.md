# PIRATE 期刊扩展：显示期限感知的分级注视点重建

状态：研究与实现方案，2026-09-28。本文中的性能门槛是实验目标，不是已有结果。

2026-10-02 速度试验更新：四组 forward Driving 输入已复制到本地，首轮 RTX 3080 测速显示原函数即使缓存 PNG 仍约 11 ms/帧，而复用缓冲区、只保留必要传输的原 kernel 流式路径约 3.2 ms/帧。GPU 预置输入时全尺寸约 1.0 ms，半分辨率底图约 0.7–0.9 ms；底图加 160×90 中央 ROI 的中位耗时约 0.81–0.85 ms，320×180 ROI 约 0.89–0.98 ms，480×270 ROI 约等于全尺寸。详见 [速度基线](../results/speed_baseline/README.md)。因此实现顺序应先处理内存初始化、缓冲区复用、未使用回传和重复参数加载，再量化局部分辨率调度的端到端增量收益；这些速度原型还没有画质和确定性验证，也不能外推到论文的 Xavier。

## 1. 已核实的起点

PIRATE 利用左右眼和相邻帧的相似性，以编码的单眼图像、视差和光流重建另一眼。论文报告 90 FPS，并在 Jetson AGX Xavier 15 W 配置下给出一帧约 9.4 ms 的分解：解码 3.2 ms、帧内重建 1.3 ms、帧间重建 2.5 ms、合成及填洞 2.4 ms。90 Hz 的帧间隔是 11.11 ms，因此按论文这些数字计算，名义余量约 1.71 ms；实际可用时间还取决于到达时刻、队列、显示合成和时钟误差。该分解不能直接当作当前 RTX 3080 的测量值。[PIRATE 论文主页](https://pure.psu.edu/en/publications/pirate-no-compromise-low-bandwidth-vr-streaming-for-edge-devices/)

仓库内的 [Driving 复现审计](../results/quality_audit/README.md) 已按原代码的 `calculate_psnr` 计算方式复跑四组序列。现有 CUDA 路径在约 0.1 bpp 的近似比较下只得到 +0.011 至 +0.177 dB；完整交替双眼码流、实际辅助信息码率及新跑的感知指标仍缺失，不能将此写作完整复现论文 Figure 9。**后续所有与原文对比的 PSNR 均调用原函数，保留 `uint8` 溢出行为，不修改该公式。**可另报独立的注视区指标，但必须单独命名、公布定义，并保留原 PSNR 列。

原始脚本以四组 `test_numba.py` 为准，数据位于 `\\YZ\2023fall1\driving__frames_cleanpass\frames_cleanpass`。以 15 mm / 300 帧脚本为例：`generate_right` 约在第 251 行，`now_to_prev` 在第 112 行做目标像素到上一帧的随机读取，`left_to_right` 在第 137 行做深度控制的视差散写，`composite` 与 `interpolate` 分别在第 196、217 行。旧实现的 scratch 初始化和竞争写入导致同帧回放并非逐像素确定。共享目录应作为只读输入，新方案写在本仓库。

## 2. 贡献边界与假设

**拟验证的贡献：**在压缩负载已经到达、码率固定之后，利用每帧至预计显示时刻的剩余时间，把重建计算分配给注视区和其余区域；先产出覆盖整幅画面的低成本结果，再在期限内逐级提升有价值的区域，并随时保留可显示的结果。重点是客户端的重建计算、期限决策和质量/期限权衡。

“注视点 + 网络状态自适应”本身不宜宣称新颖：EyeNexus 已结合眼动和网络条件调整 foveation/编码。[EyeNexus](https://arxiv.org/abs/2509.11807)  仅有“VR 帧的期限感知调度”也不新颖，已有面向网络资源的期限调度研究。[Deadline-Aware Two-Timescale Resource Allocation](https://arxiv.org/abs/2308.16419)  此方案与它们的可检验区别是：**固定传输内容、帧到达后、按剩余 GPU 时间决定 stereo reconstruction 的空间精度与何时停止**。是否足够作为期刊贡献，仍须以实测收益、消融和更新的相关工作比较证明。

核心假设分成两项，不能在实验前写成结论：

1. 局部高分辨率重建加全屏低分辨率底图，比整屏原精度重建更容易在紧张的显示期限内完成，同时维持注视区质量。
2. 将视差散写限定在输出 tile 内，并通过批处理或重排改善局部性，节省的时间大于分桶、halo、启动和合成的开销。若此项不成立，仍可只研究分级重建调度，但论文中不能声称存储访问优化。

## 3. 每帧机制

### 输入、预算与输出

输入为当前编码眼图像、视差、光流、上一帧重建眼、左右眼对应的预测注视点、帧到达时间，以及预计显示时间。在线设备若使用 OpenXR，可从 `XrFrameState.predictedDisplayTime` 获取显示目标，须在同一时钟域下计时。[OpenXR XrFrameState](https://registry.khronos.org/OpenXR/specs/1.1/man/html/XrFrameState.html)

在必要解码完成后计算

`B = t_display - t_now - T_compositor_reserve - T_safety`。

`T_compositor_reserve` 包含提交和系统合成的测量尾延迟；`T_safety` 根据时钟误差及预测误差校准。GPU 排队时间、拷贝、核函数启动和最终合成必须记入时间，不能只计 kernel 时间。接入头显前，用离线重放的显示时间线代替 OpenXR 时间戳。

1. **底图层：**在全画幅以较低线性分辨率（候选为 1/4 或 1/2）运行时间补偿、视差重建与填洞，再上采样到目标尺寸。缩放图像时，光流位移和视差像素量也必须按坐标比例变换；深度比较仍在一致的数值域内进行。启动前用实测高分位耗时判断是否可在 `B` 内完成。底图必须始终产生合法的双眼显示帧；若到达过晚、连底图都来不及，使用明确标记的上一可显示帧回退，并计为错过新帧期限。
2. **升级层：**围绕预测注视点，按 tile 将局部结果提升到 1/2 或原分辨率。中心区优先，外围区有最低质量约束。每一批 tile 完成后检查剩余预算，留出最终合成所需时间；下一批不能保守地满足预算时停止。
3. **交付层：**用确定的覆盖关系组合升级 tile 和底图，边界使用少量重叠与羽化，并以固定规则处理遮挡和空洞。交付时记录采用的层级图、注视点、预算、实际耗时及是否回退。

眼动快速跳变时，以预测注视位置和测量误差膨胀高精度中心区；一旦眼动数据缺失，采用上次可信注视点并扩大保护区。两个眼图的 tile 决策应在相应视差变换下保持一致，不能各自独立选出引发强烈双眼不一致的精度边界。

### 调度目标

设 tile 为 `i`，分辨率升级层为 `l`，每个升级有边际计算成本 `c(i,l)` 和质量收益 `u(i,l)`。收益通过离线配对帧测量，再按注视偏心角、注视不确定性、运动/遮挡和双眼一致性加权；不能单靠 PSNR 拟合视觉效用。在线问题是按“先有底图，再有较高层”依赖关系，选择升级使

`sum c(i,l) + c_final_compose <= B - c_base`

并最大化所选边际收益。第一版使用经过分桶校准的 `u/c` 贪心策略，按相邻 tile 打包以摊薄启动成本；若时间不够，停止在已完成的一层。未来可比较小规模动态规划或离线已知未来耗时的 oracle。这里的 `c` 应用设备和 tile 数量条件下的 **p95/p99 测量值**，并随运行更新；这是经验性机会约束，不是严格最坏执行时间保证。实验中报告实际期限失约率，不使用“保证 90 FPS”措辞。

### 视差散写与 tile 所有权

直接按源图小块裁剪会漏掉跨 tile 投影。对每个输出 tile，读取根据最大视差扩展过的源区，投影后只允许写该输出 tile；邻接 tile 的源区可重叠，但输出区不重叠。时间补偿属于目标像素 gather，可直接限在输出 tile。`interpolate` 的 7×7 邻域需至少 3 像素 halo。深度竞争需使用确定的最近深度选择，深度相等时用固定像素顺序打破平局；可先确定每个目标像素的获胜源像素，再 gather 颜色。输入缓冲与 mask 必须完整初始化。先做正确的 tile 版本，随后单独测试源点按目标 tile 分桶、压缩列表、核函数融合是否真的加速。tile 过小可能使重复读取和启动开销占主导，因此 tile 大小由 microbenchmark 决定。

原脚本作为历史基线保持原样。为排除原始竞争写入的方差，新方案应有一个**固定全分辨率版本**与自适应版本共享确定性重建 kernel，再额外与原 PIRATE 输出比较。这样能把新 kernel 的画质差异与调度本身的收益分开。

## 4. 实现顺序与交付物

| 阶段 | 实作 | 必要检查 | 下一阶段门槛 |
| --- | --- | --- | --- |
| A. 冻结数据和基线 | 保留四组 Driving 输入、原脚本和现有审计；记录源哈希、帧号、左右眼及码率来源 | 核对缺失帧和已有质量审计；原 PSNR 函数只读 | 明确每组可比较的帧集合 |
| B. 成本剖析 | 在目标设备逐项测量解码、上传、时间补偿、视差、填洞、合成和提交的 p50/p95/p99；全、半、四分之一分辨率及不同 tile 数 | CUDA event 与主机端时钟同时记录；暖机与 GPU 队列负载固定 | 找到能在紧预算内完成的底图候选 |
| C. 正确性原型 | 实作确定的全分辨率基线、全屏底图、输出 tile 升级、halo 与融合 | 检查零未初始化像素、无跨 tile 写、同输入逐像素重复性、双眼边界 | 质量和成本分别可测 |
| D. 在线决策 | 接入注视点、显示时间、耗时模型、分批升级与回退 | 每帧决策日志可重放；实际剩余预算包含最终合成 | 到达迟的帧也有可显示结果 |

建议在本仓库新增独立 `src/reconstruction/`、`src/scheduler/`、`bench/`、`eval/`，不要直接覆盖共享目录的 `test_numba.py`。首个可运行原型只需要“全屏低分辨率底图 + 一个全分辨率注视 ROI + 固定预算扫描”；完成逐像素和耗时检查后再加多级 tile、成本模型和内存重排。

## 5. 实验矩阵

**数据和轨迹。** 使用 15/35 mm × 300/800 帧的四组 Driving 序列，并保持每个方法相同的输入帧、编码内容和 0.1 bpp 名义点。现有数据没有可靠的 gaze 或网络到达轨迹；第一轮工程实验用中心静止、平滑跟踪、快速扫视、预测误差四类合成注视轨迹，并扫描解码后的剩余预算，例如 2/4/6/8 ms 与突发迟到。只有采集观看 Driving 的真实眼动轨迹，才能做有力的感知质量论证。公开 VR 眼动数据可用来压力测试眼动动态，但若观看内容不同，不能称为 Driving 内容的真实注视点。网络部分最好补充真实传输时间戳；否则明确标为合成 jitter 注入。

**公平比较。** 同一对照组至少包含：原 PIRATE；新确定性全分辨率实现；全屏固定低分辨率；固定注视区和固定层级；仅按期限选全屏统一分辨率；仅根据注视点选分辨率且不看期限；完整方法；离线 oracle 上界。原 PIRATE 与新实现的差异需单列，不能把 kernel 改写收益归入调度。各方法使用完全相同的帧到达时刻、注视轨迹、码率和目标硬件。若无法验证辅助码流实际码率，主表写“固定已存输入”而非“严格 0.1 bpp”，并单列名义预算。

**指标。** 主结果为 `P(deadline miss)`、晚到帧比例、p50/p95/p99 端到端显示前延迟、不同注视偏心环带质量、相同码率和失约率下的质量。将 `deadline miss` 明确定义为当前帧无法在 `t_display - T_compositor_reserve` 前提交；上一帧回退算当前帧失约，即使显示并未黑屏。画质表保留原公式的全帧/双眼 PSNR；注视区 PSNR 也应在裁切后直接调用同一原函数。另列清楚定义的注视加权质量、MS-SSIM、LPIPS、时间闪烁、边界伪影、双眼视差/融合错误和外围最低质量。CLIP 可作补充，不能替代局部细节与双眼质量。报告 GPU 功耗与每帧能耗，若设备可测；压缩/传输字节数必须验证固定。所有失约帧和回退帧都纳入统计，不能只测完成重建的帧。

**消融。** 分别去掉期限信息、注视点、不确定性扩张、局部性重排、时间补偿和回退；比较两层/三层、tile 大小、批大小、成本预测分位数及合成边界宽度。以序列或连续时间片为抽样单元做配对置信区间，避免把同一视频中高度相关的帧当作独立样本。质量收益表的训练与测试序列要分开；四组 Driving 数量少，若要支持跨内容泛化需要额外视频。

**建议的放行条件（实验目标）。** 在选定紧预算下，底图连同最终合成的 p99 必须装得下；调度和分桶开销不能抵消节省的 GPU 时间。在同一输入和 jitter 下，完整方法相对固定全精度基线显著降低失约率，同时注视区 MS-SSIM 与原精度结果接近、外围有明确质量下限，且不会引入明显双眼不适。具体阈值应先用真实设备和小规模观看实验定标，再锁定测试集；不要事后根据曲线挑选成功阈值。如果全屏底图已占满预算，需换更轻的底图或重新限定可服务的迟到范围。

## 6. 当前阻碍与下一步

1. 缺少 Driving 对应的真实眼动和网络到达时间戳；合成轨迹只适合工程可行性，不足以支持真实用户体验结论。
2. 未确认用户最终目标设备。当前 RTX 3080 只能建立原型；论文的 9.4 ms 来自 Xavier，不能跨设备外推。
3. 现有 0.1 bpp 比较仍缺完整交替双眼码流和辅助信息实际字节数。投稿前要补齐或准确限定实验主张。
4. 原始 CUDA 重建有逐像素不确定性。新 kernel 必须先保证输出确定性，且原 PSNR 不变，之后才能可信地做层级和期限比较。

最直接的下一步是阶段 B：用现有四组 Driving 中少量代表帧，在当前 GPU 上测量全屏 1、1/2、1/4 线性分辨率各阶段耗时与 tile 开销，确认“底图 + 注视区升级”是否存在可用时间窗口；同时询问或定位实际 gaze、网络轨迹和目标设备。
